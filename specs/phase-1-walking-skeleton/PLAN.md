---

## Approach

Preserve `contracts/harness-v1.openapi.json` and `contracts/run-events-v1.schema.json` as the transport-independent authority, but replace the current synchronous in-memory demonstration with a PostgreSQL-backed API, a DBOS parent workflow driving LangGraph without a checkpointer, and streamable-HTTP MCP access through the Tool Gateway. Expose the same Run capabilities through REST and a separate harness-owned streamable-HTTP MCP adapter; that adapter may create, inspect, cancel, and follow Runs but never exposes the Tool Gateway or bypasses its authority checks. This repository builds and publishes a versioned, HA-ready artefact set—signed OCI images, Helm chart, contracts, provenance/SBOMs, and an optional reusable Pulumi component—but owns no environment desired state or deployment; consuming teams deploy the immutable release with their GitOps/Argo CD process. Implement in gated stages: close the outstanding DBOS and inbound-MCP security assumptions; build transactional persistence, authority, runtime, Grafana/Kubernetes MCP integrations, streaming, audit, telemetry, and configuration control; then prove the complete system under cross-Tenant, multi-replica, crash, cancellation, dependency-outage, restore, capacity, and contract-compatibility tests.

---

## Trade-offs

- **Extend the current skeleton vs replace it wholesale** — extend the contract vocabulary and seams, but replace in-memory implementations at composition time; this preserves already-tested semantics without treating demonstration code as production infrastructure.
- **Vertical feature slices vs risk-first foundations** — prove DBOS async, scoped matching-executor restart recovery, filtering, and application-version behaviour before building around them; this deliberately delays feature breadth to avoid embedding an invalid durability assumption or an unproved cross-executor takeover.
- **One large acceptance suite vs layered suites** — use unit, schema, contract, integration, failure-injection, and end-to-end layers, with the production-like stack reserved for behaviours that cannot be proven in process; this gives fast feedback without weakening release evidence.
- **Provider-specific model integration vs LangGraph model boundary** — accept only LangGraph-compatible chat-model interfaces in graph code and confine provider configuration to composition; this proves portability without claiming support beyond upstream LangGraph and organisation policy.
- **One release vs one process** — use one chart/release for atomic compatibility and rollback, but distinct Kubernetes workloads, ServiceAccounts, listeners, secret grants, scaling policies, and network policies for the Harness API, DBOS workers, and Authority Service; operational convenience must not erase the authority boundary.
- **Pinned Run configuration vs live safety policy** — snapshot reproducibility inputs such as model resolution, prompts, budgets, and Tool definition hashes at Run creation, while re-evaluating revocation, kill switches, current principal permission, and connection throttles on every Tool call; freezing all policy would defeat the in-flight safety controls.
- **Publish deployable artefacts vs own deployments** — publish immutable, verified images, a chart, contracts, and a reusable Pulumi component from this repository; consuming teams own environment configuration, infrastructure state, GitOps promotion, Argo CD reconciliation, and operational SLOs. This preserves a supportable deployment contract without giving release CI cluster credentials.
- **REST-only vs REST plus MCP** — expose one application service through two thin transport adapters. The harness MCP endpoint reuses the same authenticated use cases, Tenant checks, idempotency, audit, and event semantics as REST and is not an alternate Tool Gateway.

### Planning Observations

- The current code is a dependency-light semantic prototype, not evidence that the infrastructure-backed acceptance criteria pass. In particular, `HarnessService.create_run()` completes synchronously and `InMemoryStore` cannot prove durability, transactional event publication, or PostgreSQL isolation.
- `migrations/001_phase1.sql` demonstrates `FORCE ROW LEVEL SECURITY` but does not yet provide the complete production schema, role/grant model, migration lifecycle, indexes, partition/retention strategy, or audit immutability proof.
- “Single deployment” means one compatible regional Helm release, not one process or Pod. The Harness API, DBOS workers, and Authority Service are separate workloads; only the Token Service, Tool Gateway, and Tool Registry co-ship inside the Authority Service deployable. MCP servers remain separate. A change to this boundary requires a superseding ADR.
- `docs/design/durable-execution.md` records successful spike results for the fundamental Pattern B boundary and separate DBOS database, while its section 9 still requires four pre-build checks. Treat the document's pinned versions as historical evidence, not automatically current dependencies.
- The DBOS system database persists inputs and outputs and is PCI-DSS in scope. The pointer rule applies to workflow/step arguments, results, messages, errors, and events—not only normal Tool return values.
- PgBouncer tests must use a non-owner, non-superuser runtime role; otherwise PostgreSQL can bypass RLS and produce false-positive isolation evidence.
- Phase 1 uses synthetic non-sensitive investigation data. The deferred production PAN-scrubbing acceptance work must not be silently represented as complete; Collector tests still prove that configured secret/sensitive-field filtering works on synthetic markers.
- OpenAI Luna, Terra, and Sol are the approved Phase 1 model aliases. Organisation policy resolves each alias to an endpoint and model configuration for the Run's home region; the resolved selection is immutable for that Run and OpenAI-specific types remain confined to configuration/composition.
- Configuration has four lifecycles: versioned Helm/Pulumi deployment inputs are supplied by the consuming team; versioned Tenant/platform policy changes through an authenticated admin API and PostgreSQL append-only publication; reproducibility inputs are snapshotted on the Run; safety controls are evaluated live per Tool call. Deployments pass opaque secret references, never values, and only the owning workload resolves them.
- Feature flags are not a substitute for policy. Any Phase 1 operational flag must be typed, default-safe, globally or Tenant-scoped explicitly, included in the configuration audit/version model, and incapable of widening Tool authority; experimental model routing remains out of scope.
- The application secret inventory is explicit: Authority Service token-signing private keys; workload mTLS private keys; inbound webhook shared secrets; OpenAI credentials for Luna/Terra/Sol resolution; Tenant-scoped Grafana service-account tokens; the HSM-backed Grafana Server Admin provisioning credential; Tenant-scoped Kubernetes authentication/impersonation credentials where workload identity is unavailable; upstream MCP/native-system credentials; and database, object-storage, telemetry-export, or backup credentials only where workload identity cannot replace them. Public certificates/JWKS, model aliases, endpoint allow-lists, database hostnames, and secret reference identifiers are configuration, not secrets. CI/release publishing uses short-lived GitHub OIDC/keyless signing where supported rather than stored cloud, registry, or signing credentials.
- Secret access is least privilege by workload: only the Token Service module can use the capability-token signing key; only provisioning workflows can use the Grafana Server Admin credential; only the Authority Service resolves Tenant Tool credentials; API/worker workloads receive only their own mTLS and data-store identity. Rotation supports overlap for in-flight tokens/connections, revocation is tested, values are never persisted by the harness, and the deployer chooses the Vault-class/KMS/HSM implementation through the published integration contract.
- Delivery responsibility is explicit: this repository and GitHub Actions validate, version, sign, and publish artefacts; Release Please controls the shared release version; the reusable Pulumi component declares infrastructure and chart inputs but holds no consumer state. Consuming teams own cloud resources, secret backends, GitOps repositories, environment values, Argo CD reconciliation, promotion, rollback execution, production SLOs, RPO/RTO, and operations. Release CI has no deployment credentials.
- Regional HA is a supported deployment property, not cross-region workflow failover: API/MCP and Authority Service replicas are stateless, workers use DBOS queues and matching application versions, durable state is external, reapers are concurrency-safe, PostgreSQL connections are pooled, and chart defaults support anti-affinity, topology spread, disruption budgets, autoscaling, and blue/green double-peak capacity. Each region remains independent and a Run recovers only in its home region.
- Grafana MCP and Kubernetes MCP are the mandatory Phase 1 customer-system adapters and remain separate streamable-HTTP deployables. The Kubernetes MCP mechanism is still marked pending in `docs/diagrams/c4-l2-containers.md`; its design and security review are therefore a Gate 2 prerequisite, not a licence to embed a Kubernetes client in the worker.
- The harness MCP endpoint is an inbound surface adapter for harness-owned Run capabilities. It is not the Authority Service's Tool Gateway MCP endpoint, does not expose registered customer-system Tools, and cannot reuse `aud: tool-gateway` tokens. Its authentication profile must resolve Principal and Tenant through the Authority Service and must trigger a reviewed design update if external client registration changes ADR-0069's threat assumptions.
- The project owner is the final approval authority for the API, security, data/RLS, durability, and observability gates; specialist review evidence and finding dispositions remain mandatory inputs to that approval.
- All dates, dependency versions, commands, expected/actual outcomes, and retained artefact locations belong in evidence. A green test without its environment and version context does not satisfy the review requirements.
